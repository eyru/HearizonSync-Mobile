## 零、什么叫「不复用前任代码」

前任 = 2026-10-22 发布的 1.1.0 那一套（4 个 Java 类 + 手工 aapt2 构建脚本 + sherpa-onnx AAR 调用层）。
本次重建的边界：

| 东西 | 用不用 | 理由 |
|---|---|---|
| 前任的 `.java` / `build-apk.ps1` / `AndroidManifest.xml` | **一个字节都不用** | 已随目录删除，也不去归档里捞 |
| 前任的包结构 `app/src/main/java/...` + aapt2 手工打包 | **不用** | 改为 Gradle 标准布局 + Kotlin |
| sherpa-onnx 依赖及其调用方式 | **不用** | 改为 ONNX Runtime + 自研前后处理 |
| SenseVoice int8 模型本体（`model.int8.onnx` + `tokens.txt`） | **用** | 这是第三方开源模型权重，不是前任代码；重下 239 MB 纯属浪费 |
| 上一版的 UI 布局、交互、文案 | **不用** | 全部重设计 |

一句话：**代码从零写，模型用公开权重。**

## 二、ADR 明细

### ADR-001 用 Kotlin + Compose
**决策**：`minSdk 26 / targetSdk 34`，UI 全 Compose，无 XML 布局。
**理由**：字幕是「高频追加文本 + 自动滚底」的列表，Compose 的 `LazyColumn` + `snapshotFlow` 处理起来比 `RecyclerView` 少一半代码；且后续要做波形/频谱可视化时 Canvas 更好写。
**代价**：APK 比纯 View 大 2–4 MB（Compose runtime），可接受。

### ADR-002 用 Gradle，不再手工打包
**决策**：标准 `app/` 模块 + Kotlin DSL（`build.gradle.kts`）。
**理由**：手工链的五个坑（路径硬编码、输出名硬编码、版本号不同步、外部 toolchain 依赖、无工程结构）本质都是「没有构建系统」。用 Gradle 一次性消掉。
**代价**：首次构建要联网拉 AGP/Compose（约 1–2 GB），之后走缓存。

### ADR-003 推理走 ONNX Runtime，前后处理全部自研
**决策**：
- 依赖：`com.microsoft.onnxruntime:onnxruntime-android`（官方 AAR，含四架构 `.so`）
- **自研**：log-mel fbank（80 维、25 ms 窗 / 10 ms 帧）、归一化、VAD 门控、CTC 贪心解码 + 重复折叠、标点/断句后处理
- **不用** sherpa-onnx：它的 `OfflineRecognizer` 把前端参数锁死，做不了「噪声底自适应」「远场增益归一」这类我们要的调优

**验收标准（关键）**：同一段 wav，Python 参考实现与 Kotlin 实现的 fbank 输出，**逐帧最大相对误差 < 1e-3**；识别结果字符串完全一致。

### ADR-004 音频直采
**决策**：`AudioRecord(MIC, 16000, MONO, PCM_16BIT)`，8 KB 环形缓冲，子线程读 → 送 VAD → 送特征。
**理由**：识别模型要 16k 单声道；`MediaRecorder` 会先编码成 AAC 再解，白折损一层。

### ADR-005 翻译走本地离线 opus-mt（推翻原先「只走在线」的判断）
**原判断**：曾计划只走在线（MyMemory / DeepSeek / 有道三路互不降级），理由是桌面版的本地翻译依赖 CTranslate2，而 Android 上没有可用绑定。
**推翻理由**：CTranslate2 不可用 ≠ 本地翻译不可行。opus-mt-zh-en 已有现成的 ONNX 权重（Xenova 转换版），MarianMT 本身是标准的 encoder-decoder Transformer，用 ONNX Runtime 分别跑 encoder / decoder，配自研 sentencepiece 分词 + 贪心生成即可，**不需要任何翻译专用运行时**。
**结果**：离线翻译已跑通，译文与桌面版观感相当（逐句结果见进度文档）。产品「完全离线、不联网也能用」的定位因此保住，不必向主人认「翻译只能联网」这笔账。
**代价**：APK 多 113 MB（encoder 52.9 MB + decoder 59.8 MB 量化模型）；单句解码约 100–200 ms（模拟器），放在独立 `mt-worker` 串行队列里异步做，不阻塞中文字幕出字。

### ADR-007 VAD 噪声底用「滑动窗口 10 分位」，不是指数平滑
**背景**：初版用滑动平均递推噪声底（`floor = 0.995*floor + 0.005*rms`）。实测同一段 10.3 秒连续语音会被切碎成 8–9 段、CER 0.486–0.657。
**根因**：指数平滑在持续语音时噪声底被语音能量抬着往上爬，弱音帧被判成静音 → 句子被切成碎片、字被吞。
**决策**：维护 150 帧（3 秒）环形窗口，取 10 分位作为噪声底；不足 20 帧时退回绝对下限 0.003；阈值 `max(分位底 × 2.6, 0.003)`。
**实测**：同一段语音切 4 段、总时长 9.12 s（原文 10.3 s）、**CER 0.000**；5 秒窗结果相同，故取 3 秒（切句响应更快）。
**代价**：每帧一次窗口排序（150 个 float），在 20 ms 帧率下开销可忽略。

### ADR-008 幻觉字幕用文本级规则拦，不用置信度
**背景**：静音或纯噪声时 SenseVoice 会稳定吐出「我。」「。」，音乐/键盘/电视环境下更会连续刷「嗯。」——离线字幕产品出现这个等于废掉。
**排查结论**（逐一否掉，避免后人重复试）：
| 判据 | 结果 |
|---|---|
| 平均帧置信度 | 真语音 0.602–0.985 / 噪声 0.709–0.967，**完全重叠**，不可分 |
| 声学特征（谱平坦度 / 过零率 / 峰值比 / 谱通量） | 全部不可分 |
| 周期性 voicing | 最可用但边界重叠，且音乐（voicing 0.34）挡不住、真语音误杀严重 |
| 模型自带 `<\|nospeech\|>` | 只是把输入 language token 回显成输出首 token，**不是检测器** |
| 模型事件 token `<\|Speech\|>` 等 | 真语音与噪声里都只出现 1 帧，**无区分力** |
**决策**：纯文本级——段长 ≥ 1.2 s 一律放行；段长 < 1.2 s 时，核心字数（去标点空白）< 2 或全为语气词（嗯啊哦呃唉诶呀哈嘿…）则丢弃。
**实测**：音乐 40 条 → 0 条；键盘 5 条 → 0 条；电视 1 条 → 0 条；真语音 4 段一段不少。

### ADR-009 「句尾降噪」实现但默认关闭
**背景**：桌面版 v2.5.6 的帧级噪声门（20 ms 分帧、10 分位噪声底、低于底噪帧衰减 0.3）宣称「底噪 −55.8%、语音保留 100%」。
**实测（8 个带噪样本 + 同段语音加白噪）**：
| SNR | 降噪关 CER | 降噪开 CER |
|---|---|---|
| −5 dB | 0.914 | **0.886** |
| 0 dB | **0.657** | 0.714 |
| 5 dB | 0.429 | **0.371** |
| 10 dB | **0.086** | 0.143 |
| 15 dB | 0.000 | 0.000 |
| 平均 | **0.417** | 0.423 |
**结论**：平均没有收益，且开启后会把键盘噪声从 0 条幻觉放大到 3 条。桌面版那两个数字是**能量指标**，不是识别率指标——这是最容易误导后来人的地方。
**决策**：`Denoiser` 保留并在设置页提供开关，**默认关闭**；只作为「底噪极大的环境」下的兜底手段，量产不默认开。

### ADR-010 导出走 MediaStore，不申请存储权限
**决策**：Android 10+ 用 `MediaStore.Downloads` 写入 `Downloads/HearizonSync/`，`IS_PENDING` 两段式提交；API 26–28 落应用外部目录 `Android/data/<pkg>/files/Downloads/exports/`。
**理由**：申请 `WRITE_EXTERNAL_STORAGE` 只会让用户犹豫；MediaStore 免权限、文件出现在「下载」里用户能找到。
**代价**：API 28 及以下的文件不在公共下载目录，需要在设置页显示实际路径（已实现「上次导出：…」提示）。

## 四、承认的风险

1. **自研 fbank 容易「差一点点」**：mel 滤波器组、窗函数、CMVN 的细节与训练配置不一致，识别率会明显掉。→ 用 Python 参考实现当金标准，先对齐数值再谈效果。
2. **239 MB 模型 + 60 MB 运行时，APK 会到 300 MB 量级**：可接受（老版 288 MB），后续可做模型量化/分架构分包。
3. **无真机**：只能靠模拟器验证功能，不能验证真实收音与功耗。这一条必须如实告知主人。

## 五、v2.0.0 真机落地后补记（2026-10-27）

### ADR-007 麦克风音源用 `MIC` 而非 `VOICE_RECOGNITION`
**背景**：真机（vivo V2254A / Android 16）首版「只能靠喊才收得到」。
**根因**：`VOICE_RECOGNITION` 是给通话近讲调优的源，国产 ROM 会叠加强降噪 + 距离压制，输入电平被压到 VAD 地板以下。
**决策**：音源改 `MediaRecorder.AudioSource.MIC`（原始麦克风），叠加两层增益：
1. 硬件 `AutomaticGainControl` + `NoiseSuppressor`（`runCatching` 包住，各家 ROM 支持不一，拿不到不拒绝启动）；
2. 软件 AGC：目标峰值 0.45、上限 8 倍、峰值包络衰减 0.94、增益平滑 0.85/0.15。
同时把 `VadEnergy.absFloor` 从 0.003 降到 0.0012（约 −58 dBFS）。
**注意**：软件 AGC 不改变信噪比，只是把电平抬到 VAD/模型舒服的区间；不会让噪声里的识别变准，幻觉仍靠文本过滤拦。

### ADR-008 中英双向翻译 + 自动语种判定
**背景**：首版只有 `opus-mt-zh-en`，用户说英语时 SenseVoice 输出英文，再喂「中→英」模型等于把英语当中文再翻一遍，界面上就是「说英语、输出英语」。
**决策**：
- 内置两个方向模型（各 ~113 MB）：`mt/`（zh→en）、`mt_en_zh/`（en→zh）；
- `LangDetect` 按字符类别判语种（假名→日、谚文→韩、汉字占比≥15%→中、拉丁≥50%→英），不引入额外模型；
- 默认方向 `auto`：中文句走 zh→en，英文句走 en→zh；
- 英→中模型**懒加载**（第一次遇到英文才落盘 + 装载），不拖慢首次启动，也不让只讲中文的用户白占 113 MB；
- 识别语言默认 `0=自动`（SenseVoice 的 LID），设置页可强制中/英/日/韩。
**已知缺口**：日/韩/粤目前**能识别、不能翻译**（没有对应 MT 模型），只出字幕。补一个语种约 +113 MB，按需再加。

### ADR-009 图标
首版 `res/` 下没有任何 mipmap，用的是系统默认图标。现从桌面版 `icon.png`（512×512，主色 `#036954`）生成全套：
传统 `mipmap-*dpi/ic_launcher(.round).png` + 自适应图标（`drawable-*/ic_launcher_foreground.png` + `mipmap-anydpi-v26/*.xml` + `values/ic_launcher_background.xml`）。
生成脚本：`工具/生成图标.py`。

### ADR-012 小语种：四方向模型 + 两跳级联
**背景**：用户要求「语言包打包全」。实测 `opus-mt-ja-zh`、`ko-zh`、`opus-mt-tc-big-ja-zh` 在 hf-mirror 上全部 404——「小语种→中文」的直译模型不存在。可用的只有 `Xenova/opus-mt-ja-en`（110MB）与 `opus-mt-ko-en`（113MB）。
**决策**：日/韩走「→英→中」两跳（`ja→en` 再 `en→zh`，复用已有英中模型）。四方向全部内置，APK 从 434MB 涨到 **734MB**（769,915,054 B）。
**踩到的坑（重要）**：`opus-mt-ja-en` 的 `vocab_size=60716`、`pad/decoder_start=60715`，其余三个模型是 `65001/65000`。Kotlin 原本把 `SpmTokenizer.PAD=65000` 写死，导致日→英解码起点越界、输出空串——现象正是「日语能识别、不能翻译」。现 `MarianTranslator` 增加 `padToken` 参数，日→英传 `60715`。
**质量备注**：日→英好（「こんにちは、今日はいい天気ですね。」→ "Hello, it's a nice day today, isn't it?"）；韩→英偏弱（`안녕하세요. 오늘 날씨가 좋네요.` → "Good morning. Good day."），两跳后中文有偏差，属模型上限。
**已废弃路线**：`Xenova/opus-mt-mul-en`（单模型多语言→英）的 onnx 量化版解码全是 `<pad>`，试过 decoder_start=64171/0 都不行，判定为转换损坏。

### ADR-013 译文清洗：滤 UNK、折叠重复、按逗号去重
贪心解码在个别句子上会吐出一串 `<unk>`（id=1）或同一个 token 连续重复（「早早早早」）。三层处理：
1. `MarianTranslator.render` 直接跳过 `EOS / padToken / UNK`；
2. 重复保护：连续 3 个相同 token 立即停止解码；
3. `AppScreen.tidy()`：去 `<unk>/<pad>` 文本 → 整串是同一片段 3 次以上重复则折叠成一次 → 按逗号去掉完全重复的片段；清洗后为空则不显示译文。
**注意**：这些是模型输出层的兜底，不是识别错误；真语音的重复音节（「哈哈哈哈」）也会被折叠，属可接受代价。

### ADR-014 顶栏语言切换 + 设置页翻译自测
- 顶栏加语言胶囊（`DropdownMenu`）：自动 / 中→英 / 英→中 / 日→中 / 韩→中，不进设置页就能切；
- 设置页「翻译自测」：四方向各跑一句固定样例并回显结果，模型缺失或参数错时把异常原文打出来——这次的 pad 问题就是靠它定位的；
- 设置页「关于」里的翻译模型说明同步改成四方向。

### ADR-015 选方向必须同时锁定识别语言
**现象**：主人反馈「日语好了，但韩语还是会识别成中文或者日语」。
**根因**：`SenseVoice` 的 `language` 参数是逐段喂进去的 token，`0=auto` 时模型自己猜。韩语音系与中文/日文接近，噪声与短句上尤其容易猜错，输出直接变成中文/日文——翻译再准也救不回来。
**决策**：切换翻译方向时联动设置识别语言（`AppScreen.applyDirection`）：
| 方向 | asrLanguage |
|---|---|
| 自动 | 0（auto） |
| 中→英 | 3（zh） |
| 英→中 | 4（en） |
| 日→中 | 11（ja） |
| 韩→中 | 12（ko） |

会话创建时语言就固定了，所以正在监听时切方向会重开一次会话（`stopListening()` + `startListening()`）。
**兜底**：即使方向锁死，识别文本语种仍可能不符（偶尔整句被判错），`translateText` 先 `LangDetect.detect()`，语种与方向不符就回退到自动选路，避免把中文硬喂进「韩→英」模型。

### ADR-016 幻觉过滤第二版：按内容强度判，而不是只按段长
**现象**（主人真机反馈）：不说话的时候会蹦出 `Yeah.`、`一`、以及日语/韩语的无意义单字符，会污染字幕和导出文件。
**第一版为什么漏**：旧规则是「核心字符 < 2 **且** 段长 < 1.2 s」+「全是中文语气词」。三类漏网：
1. 英文填充词（`yeah`/`oh`/`okay`）字面长度够，中文语气词表管不到；
2. 呼吸/键盘尾音把段拖过 1.2 s，单字规则失效；
3. 日语韩语单字符（`い`/`어`）不在中文语气词表里。
**第二版规则**（`TranscriptFilter.isHallucination`，顺序执行）：
1. 核心字符 < 2 → 丢（「我」「一」「い」「어」），**不再看段长**；
2. 去重后只剩 1 种字（「一一一」「呃呃呃」）→ 丢；
3. 全是中文语气词 → 丢；
4. 单个英文填充词（`yeah/oh/okay/well/the…`）→ 丢；
5. `expectLang ≠ detectedLang` 且核心字符 < 4 → 丢（模型自判语种来自输出首部 `<|zh|>` 标签，见 `SenseVoiceEngine.recognizeEx()` 返回的 `lang`）；
6. 段长 < 2 s 且两字产物里夹着语气词（「啊一」「嗯呀」）→ 丢；
7. 极短段（< 0.7 s）核心字符 < 3 → 丢；
8. 短段（< 1.2 s）核心字符 < 3 且全是语气词 → 丢。
**代价**：真人单字回答（「好。」「是。」）也会被丢掉——离线字幕产品里，这类独立单字段落极少，宁漏不错是明确取舍。
